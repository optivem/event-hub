## TL;DR

**Why:** Keycloak still carries the names it was ported with from `optivem/shop`: realms `shop` (acceptance and QA share it) and `shop-prod`, client `shop-frontend`, and "Keycloak shop" in the deploy logs. Because acceptance and QA share one realm, both deploys write the same client's URLs and mix test users and sessions. The deploy signs in as the temporary bootstrap `admin` user, so that user can't be deleted, which Keycloak warns about on every console visit. Users can only sign in with a Keycloak password.
**End result:** Each stage has its own realm, `${SYSTEM_NAME}-acceptance`, `${SYSTEM_NAME}-qa` and `${SYSTEM_NAME}-prod`, with client `${SYSTEM_NAME}-frontend`. The deploy authenticates with a dedicated, narrowly scoped service-account client; Keycloak has no temporary admin user or client, and a rebuild still needs no manual step. On QA and prod the login page offers "Sign in with Google" next to the password login, for invited users only: an admin creates the user first, and the first Google sign-in links to that account on a verified email. A `/privacy` page explains what personal data is kept.
**Unchanged:** password login; the roles (`CUSTOMER`, `ADMIN`) and how admins assign them; acceptance and QA test users and the automated tests, which keep signing in with passwords; acceptance has no Google login; the prod realm stays hardened (no test users).

## Resolved decisions

- **Q1 Bootstrap of the deploy client (2026-11-04):** Keycloak starts with a temporary bootstrap service-account client (`KC_BOOTSTRAP_ADMIN_CLIENT_ID` / `KC_BOOTSTRAP_ADMIN_CLIENT_SECRET`) instead of the `admin` user. `./setup-gcp.sh` generates its secret into Secret Manager. On the first deploy against a new master realm, the deploy uses it to create the permanent, narrowly scoped deploy client (secret `${SYSTEM}-keycloak-deployer-secret`), then deletes the temporary client. **Why:** no temporary admin user or client remains, and a rebuild still needs no manual step
- **Q2 Realms with Google login (2026-11-04):** `${SYSTEM_NAME}-qa` and `${SYSTEM_NAME}-prod`, not acceptance. **Why:** QA tests Google login before prod; the acceptance tests use password users
- **Q3 Who may sign in with Google (2026-11-04):** invited users only. An admin creates the user (with their email) in the realm first; Google login then links to that account. A Google account with no matching user gets an error and no account is created. Roles come from the invited user, not from the first login. **Why:** user decision; keeps sign-up closed
- **Q4 Linking a Google login to the invited account (2026-11-04):** link automatically when Google reports the email as verified and it matches an existing user (first-broker-login flow: *Detect existing broker user* → *Automatically set existing user*, with the IdP's *Trust email* on). An unverified Google email is rejected. **Why:** only admins create accounts (Q3), so nobody else can claim the email first, and invited users who never set a password can still sign in
- **Q5 Privacy policy (2026-11-04):** this plan adds a static `/privacy` page to the frontend (new Step 4), linked from the footer and used as the consent screen's privacy policy URL. Claude drafts the text, the user reviews it before prod. The consent screen is published "In production" with only `openid email profile`, so no Google verification review. **Why:** the repo has no privacy page, and GDPR needs a privacy notice anyway because the app stores names and emails
- **Q6 OAuth client project (2026-11-04):** a small dedicated, long-lived Google Cloud project (for example `event-hub-oauth`) owns the consent screen and the OAuth client, not `event-hub-*` and not `tfstate-995925`. The client ID and secret are kept in that project's Secret Manager; `./setup-gcp.sh` copies them into the new `event-hub-*` project's Secret Manager, so the deploy reads them locally and a rebuild needs no manual step. **Why:** teardown deletes `event-hub-*`; a project has one consent screen with one app's branding, so shop gets its own when ported
